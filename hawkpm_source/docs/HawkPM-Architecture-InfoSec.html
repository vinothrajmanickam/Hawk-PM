HawkPM — Organizational Architecture (Information Security Review)

Purpose: Present the end-to-end solution architecture and security controls for HawkPM (Project Management portal) to obtain Information Security approval prior to AWS deployment.

Scope: Two fully isolated environments (UAT and Production). Hosting on the organization's AWS account; identity via Microsoft Entra ID (SSO).

1. Architecture Diagram

Corporate / Identity AWS Edge / Public AWS Private (no internet) Data at rest (encrypted)

2. Request Flow (numbered on diagram)

  1. SSO: User authenticates to Microsoft Entra ID (MFA + Conditional Access enforced by the bank). The browser receives a signed OIDC token.
  2. HTTPS to edge: Browser requests the app; traffic passes AWS WAF then CloudFront (TLS 1.2+, HTTPS only).
  3. App load: CloudFront serves the static SPA from a private S3 bucket (via Origin Access Control; bucket not public).
  4. API calls: SPA calls the REST API over HTTPS, presenting the Entra ID token; API Gateway's JWT authorizer validates it before any logic runs.
  5. Data: Lambda (in private subnets) enforces role-based rules and reads/writes the encrypted PostgreSQL database (no public IP).
  6. Attachment broker: For files, Lambda issues a short-lived pre-signed S3 URL (scoped to one object, time-limited).
  7. File transfer: Browser uploads/downloads the file directly to the private attachments bucket over HTTPS using that pre-signed URL. File bytes never transit the database; the DB stores only metadata.

4. Security Controls (for InfoSec)

DomainControl
Identity & AccessEntra ID SSO (OIDC) with MFA + Conditional Access; API validates JWT on every request; application RBAC (Super Admin / Admin / PM / App Owner / Viewer) enforced server-side.
NetworkDatabase and compute in private VPC subnets with no public IP; S3 buckets private (no public access); only CloudFront + API Gateway are internet-facing, fronted by WAF.
EncryptionTLS 1.2+ in transit everywhere; AES-256 at rest via KMS for S3, RDS/Aurora, and Secrets Manager.
Data segregationUAT and Production are fully isolated: separate accounts/VPCs, buckets, databases, keys, and pipelines. No shared data.
AttachmentsStored in a dedicated private bucket; access only via short-lived pre-signed URLs scoped to a single object; file-type/size validation at the API; S3 versioning for recovery.
Least privilegeIAM roles scoped per service and per environment; CI/CD deploy role limited to its environment's bucket + CloudFront invalidation.
Logging & auditCloudTrail (API/account activity), CloudWatch (app/infra logs), CloudFront + S3 access logs; application maintains its own change/approval audit trail (maker-checker deletion workflow).
SecretsNo secrets in source or client bundle; DB credentials in Secrets Manager; the SPA holds no server secret (public SSO client with PKCE).
ResilienceS3 durability + versioning; automated DB backups / point-in-time recovery; infrastructure reproducible via IaC/pipelines.
Key assurance for InfoSec: The static front-end holds no secrets and cannot reach the database directly. All data access is brokered by an authenticated API that validates the corporate SSO token and enforces role permissions server-side. Attachment files are isolated in a private, encrypted bucket accessed only through time-limited, single-object pre-signed URLs.

5. Assumptions & Items for InfoSec Confirmation

  • Internet exposure: confirm whether the app is internal-only (VPN/corporate network) or public with WAF/IP allowlisting.
  • Database engine standard: Aurora Serverless v2 / RDS PostgreSQL assumed (relational, audit-friendly). Confirm org preference.
  • Data residency / region: confirm the AWS region(s) permitted for bank data.
  • Retention: confirm retention and backup policies for DB and attachments; archival-project data is retained per the application's deletion workflow.
  • DLP / malware scanning: confirm if uploaded attachments must be scanned (e.g., antivirus) before storage.
  • Key management: confirm customer-managed KMS keys (CMK) vs AWS-managed.
